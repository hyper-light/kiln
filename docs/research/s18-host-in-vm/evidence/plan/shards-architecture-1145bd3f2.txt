22975: ### D236. A network's destinations: a member reaches the hosts its grants name, the host itself at one port (built; real-VM validation owed)
22976: 
22977: **Why.** Kiln plan 01a1cd8e862e7169a074db3d5fa33f3d, step 9, and the harness bring-up's
22978: finding H2 (docs/research/measurements/harness-bringup-v1): an Agentfile's egress named
22979: ports alone. `NETWORK --egress=443` with `EXPOSE 443 AS egress` let a harness open TCP 443 to
22980: any address past its microVM, and `--dns` let it resolve any name, where Codex needed
22981: `api.openai.com` and `chatgpt.com` alone. Nor could a member reach kiln's MCP, served over
22982: HTTP at `/api/mcp` on kiln's `http_addr` (`0.0.0.0:7070` by default, kiln
22983: `crates/kiln/src/config.rs`): the host itself is what `Policy::Ports` never reaches (its
22984: gateway and loopback refused, rootless-security.md R4.16). Only a remote `MCP` server's grant
22985: named a host (D59 part seven); a run's command had D192's.
22986: 
22987: **Alternatives.**
22988: - *A directive of its own* (`EGRESS host:port FOR member`): a second grammar for what a
22989:   network's boundary says already, where D192 put destinations on a network. Not taken
22990:   (R13).
22991: - *Names held by what a flow says* (TLS SNI, HTTP Host: Squid's ACLs, cloud firewalls'
22992:   FQDN rules): a client chooses what it says (domain fronting; ECH hides SNI). Not taken: a
22993:   flow reaches the addresses its resolver path answered, which is what D59 holds.
22994: - *Learned addresses held per member in the guest* (Cilium's toFQDNs policy programs each
22995:   endpoint's allowed addresses from the DNS answers its proxy relays; dnsmasq's `--nftset`):
22996:   D192's "held apart by the address its flows come from". Not built here: what the union
22997:   cannot hold is refused instead (below), which lifts once it is.
22998: - *The host at an address of its own* outside eth0's subnet (Docker Desktop's
22999:   192.168.65.254, Lima's 192.168.5.2): any such address can be one of a user's own
23000:   networks. The gateway is never a destination (it is the network process), and D124 takes
23001:   it for the host's loopback already.
23002: 
23003: **Decided.**
23004: - *Grammar.* `NETWORK --egress=HOST:PORT`, beside ports: TCP; HOST a host's name (RFC 1035
23005:   §2.3.1 and RFC 1123 §2.1 labels, the last not all digits, RFC 3696 §2, so that no port or
23006:   mapping reads as one), an IPv4 address, or `host.docker.internal`, the host itself (Docker
23007:   Desktop's name for it; `.internal` is the top-level domain ICANN reserved for private use,
23008:   2024, so no name in the DNS is it). Refused, saying why: one on `--expose` or `--ingress`
23009:   (a destination is reached, never let in), on a network carrying no TCP, a pattern, an IPv6
23010:   address (as D192), UDP, and `localhost` (the asker's own, RFC 6761 §6.3). One parser,
23011:   `shards_dns::destination`, reads D192's option and the Agentfile.
23012: - *Who, to whom, which port, which way.* The network's members (`CONNECT … ON` it, within its
23013:   `FOR`) for whom the microVM's boundary opens the port outward (`EXPOSE … AS egress`, or both
23014:   ways, `FOR` it; D122's `--agents` and `--harnesses` naming them): the host named, at its
23015:   port, out. Two boundaries, as a port's (§12 answer 6); an internal network's reach nothing.
23016: - *Names.* A member asks the agents' resolver for its destinations' names alone, as a remote
23017:   MCP server's (`--dns` neither needed nor implied). The host itself is in its hosts file at
23018:   eth0's gateway and never asked of a resolver: the network process forwards no question for
23019:   it. A remote MCP server's URL may name the host itself too (`MCP kiln FROM
23020:   http://host.docker.internal:7070/api/mcp FOR codex`, kiln's MCP), which its grant then is.
23021: - *Held.* The network process's policy names each destination beside the MCP servers'
23022:   (`encode_policy`): a flow to its port reaches only an address its resolver answered for the
23023:   name through it, or the address it is; the host itself is the gateway at that TCP port
23024:   alone, which it takes to the host's IPv4 loopback there (`Config::host_side`). The guest
23025:   lets the member out on that port (its gate, the switch, init's forward chain); the run's own
23026:   processes (`confine_eth0`) and its engine's members (D181) reach the gateway by TCP at its
23027:   resolver's port alone.
23028: - *Refused where it cannot be held* (`agentfile::held`, at build and as the daemon reads the
23029:   normalized Agentfile): the network process holds the whole microVM to the union of its
23030:   members' names on a port, and a member's init lets it out on that port to any address. So
23031:   on a TCP port that one member reaches by name (a destination, or a remote MCP server), every
23032:   other member granted the port is granted the same names and none a port grant of it; else
23033:   the image is refused, naming both members and what each reaches. Remote MCP servers beside
23034:   another member's other grants on one port, which passed before, are refused alike.
23035: - *Orchestrators* keep or drop destinations (`Narrowing.destinations`, D231, channel version
23036:   3), never add one. The build labels them (`vnd.osi.agentfile.destinations`) for Docker and
23037:   Kubernetes; the daemon holds a run to its own reading of the image (D109).
23038: 
23039: ```dockerfile
23040: HARNESS codex FROM ./codex
23041: NETWORK --egress=api.openai.com:443 --egress=chatgpt.com:443 --egress=host.docker.internal:7070 provider FOR codex
23042: EXPOSE --harnesses=codex 443 7070 AS egress FOR provider
23043: CONNECT codex WITH codex ON provider
23044: ```
23045: 
23046: **Literals.** `host.docker.internal`, Docker Desktop's documented name; TCP port 53, DNS's
23047: (RFC 1035 §4.2.2), the gateway's one service to the run's processes; 63, a label's most, and
23048: 253, a name's as text, its 255 octets on the wire less its first length and the root's (RFC
23049: 1035 §2.3.4), as D192 had them. No bound, wait or size of its own.
23050: 
23051: **Evidence.** The implementer's record, light tests on Linux x86_64 (adacachy) and the
23052: supported targets' lint: docs/research/measurements/s9-grants-v1.
23053: 
23054: **Evidence owed** (ROOT). On real microVMs (KVM, HVF, WHP): a member granted provider names
23055: reaches them and nothing else (another host on their port, another port, an address no answer
23056: gave), and resolves them alone; one granted `host.docker.internal:PORT` reaches a listener on
23057: the host's loopback at PORT and no other port of the host, while the run's own command and
23058: another member reach neither; an image `held` refuses fails its build, and its run when
23059: crafted. The bring-up's examples (docs/examples/harness-codex, harness-claude) moved to
23060: destinations once run so.
23061: 
23062: **What would falsify it.** A provider whose clients reach it at addresses its names never
23063: answer (then address ranges as grants); a member that must reach one port by name beside
23064: another member's other names (then the per-member hold above, which lifts the refusal).

23395: ### D240. A member's stdio, terminal and environment, as a harness is driven (stdin, stdout and stderr built: plan step 5; environment, home and working directory built: step 7; exec, attach and a terminal building: step 6; real-VM runs owed)
23396: 
23397: **Why.** Kiln plan 01a1cd8e862e7169a074db3d5fa33f3d runs a harness as a HARNESS member under
23398: shards-init (D54, D59) and drives it as kiln drives one on a host: over its stdio (Claude
23399: Code's stream-json, Codex's app-server, ACP), with its sign-in and its own screen on a
23400: terminal, its config, sign-in state and transcripts under its HOME, at work in its project.
23401: When the plan began a member had `/dev/null` for stdin; `HOME=/tmp`, `PATH` and `SHARDS_DOMAIN`
23402: alone, none of its image's `ENV` and nothing set at run time; a read-only working directory;
23403: and no exec, attach or terminal (the plan's steps 5, 6 and 7).
23404: 
23405: **Decided and built.**
23406: - *stdin, a stream its owner holds* (step 5, e7825cb32; managed-runtime-plan.md P3's input,
23407:   G24). Closed (`/dev/null`) unless its owner asks for it as the run is made: the daemon's owner
23408:   by the run's `shards.stdin` annotation, an orchestrator by `MemberSpec::stdin`
23409:   (`ImageGuest::take_input`, a pipe's write end, on shards-api's wire version 6). Exact bytes;
23410:   vsock's credit is the backpressure; the owner's end and abort are typed, and the member's end
23411:   is told once (`MANAGED_INPUT_ENDED`). Only its owner writes it: through the managed endpoint
23412:   (AES-256-GCM, D239; the owner's key pinned), one record in flight, resumed a record behind and
23413:   never ahead; an owner's lost connection takes nothing from the member. Design, literals and
23414:   tests: D180's "A member's stdin, a stream its owner writes";
23415:   record: [member-stdin-v1](../research/measurements/member-stdin-v1/README.md). Its
23416:   connections are admitted as an exec's are (D16, "An exec's connection").
23417: - *stdout and stderr, captured whole* (P3). Each channel apart, its bytes as the member wrote
23418:   them, credited by its reader; an observer's going ends no member (D180's "Managed
23419:   owner-output transport"; D231's "Members' streams and ends").
23420: - *Its environment* (step 7, 239749c60). Init's, then the image's `Env`, then its own
23421:   `run.env`, then what its run stages, the last given of each name winning. `PATH` keeps the
23422:   member's own programs first; `HOME` is never the image's; `SHARDS_DOMAIN` is refused at the
23423:   build, at the daemon's and the run host's reading, and in init (D59, "A member's
23424:   environment: init's, the image's, its own, its run's").
23425: - *Its home* (step 7, ac9bb8589). Writable and its own: its scratch at `/tmp`, or a writable
23426:   volume its run gives it, the deepest that holds its `HOME`. What is staged for it lands there
23427:   (D231, "Staging"). A volume at or under `/tmp` is refused at build and at run, as the scratch
23428:   is the domain's own (D109, "A domain's `/tmp` is its own";
23429:   [s7-scratch-volume](../research/measurements/s7-scratch-volume/README.md)).
23430: - *Its working directory* (step 7, d6ac7e48f). The project path its run names
23431:   (`MemberSpec::workdir`), absolute and plain, refused relative or escaping at each end
23432:   (D231). A project plugged into a running member is not the working directory of one that
23433:   started before it (D235), so the project must be at its path as the member starts: a
23434:   boot-time path for that is owed, D235's and the orchestrator's to choose (D231).
