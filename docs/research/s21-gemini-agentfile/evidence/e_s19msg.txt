3. One multi-platform build per harness, not a harness × arch matrix. build-image@v1 pushes the same `<repo>/images/<name>:<tag>` from each leg, so amd64 and arm64 legs would overwrite each other's tag instead of making one index. The context instead holds per-arch directories, `HARNESS <id> FROM ./<id>-${TARGETARCH}[-<variant>]` with `ARG TARGETARCH` redeclared in the stage. A HARNESS source expands ARGs; see shards' build.rs test "Expanded where it is laid out too". One `shards build --platform linux/amd64,linux/arm64` makes the index. With no RUN (true of glibc bases), nothing runs under emulation. The workflow's matrix is per harness; per-arch smoke legs follow, arm64 on a Mac Studio runner.
4. Verify at pin time; fetch at build time by sha256 only, with one shared fetcher. Keep your publisher checks (npm registry signature; Node's SHASUMS256.txt.asc GPG; Claude's GPG-signed manifest; Codex's cosign) in `.kiln/images/harness-<id>/pin.sh`. That script verifies and writes pin.json: the version, how it was verified, the base digest, and per build {platform, variant if any, files: [{url, sha256, size, path, mode, unpack if an archive}]}. The build-time fetch is kiln's own `kiln agentfiles context <id> DIR [--platform …]`, written once in step 19. It downloads each pinned file, checks size and SHA-256 as it streams, and lays out the per-arch dirs. CI and kiln's local-build fallback then use the same code, on every host including Windows, with no gpg, cosign or npm on a user's machine.
   - Claude needs no unpacking. You (Node .tar.xz, npm .tgz) and Codex (.tar.gz) do: add `unpack` to the shared fetcher in your step if step 19's hasn't landed it.
   - The fetched per-arch dirs are generated into a temp context, never committed. Only Agentfile, harness.json(s), pin.json and pin.sh live in `.kiln/images/harness-<id>/`.
